01 概要と設計原則

目的

コーディングの主役が AI エージェントになることを前提に、エージェント（Claude）が少ない手戻りで正しく書け、少ない文脈で正確に読める言語を作る。人間が読み書きする場面は想定しない。短さや書き心地よりも、明示性と規則の少なさを優先する。

実行環境は Android（ART）。kata のソースは JVM バイトコードに直接コンパイルし、DEX に変換して APK にする。Kotlin には依存しない。

前提となる制約

kata は新しい言語なので、エージェントの学習データに存在しない。この不利は次の3つで補う。

  1. 仕様を小さく保ち、必要な章を丸ごとコンテキストに載せられるようにする。
  2. 構文の見た目は既存の言語（Rust、Swift、Kotlin）に寄せ、意味論だけを厳格にする。
  3. エラーは機械可読にし、何をどう直せばよいかをコンパイラが返す。

設計原則

規則を足すか迷ったときは、この原則に照らして決める。

ID原則具体的な規則
P1書き方は1通りオーバーロード、既定引数、暗黙の型変換、演算子の自作、シャドーイングを持たない。引数は名前付きで宣言順に書く。
P2省略しない型注釈、return、self.、import をすべて明示する。型推論はしない。
P3読む範囲を閉じる継承を持たない。フィールドを書き換えられるのはそのクラスのメソッドだけ。ファイルが使う外部の名前はファイル先頭の import にすべて現れる。
P4暗黙の優先順位に頼らない種類の違う演算子を混ぜるときは括弧を必須にする。
P5null と例外を持たない値がないことは Option、失敗は Result で表す（M2）。回復できない誤りはパニックとしてアプリを止める。
P6通るか通らないかの二択警告は存在しない。診断はすべてエラーで、未使用の import もエラーになる。
P7エラーは検査の1か所で出す検査を通ったプログラムはコード生成で失敗しない。

言語の性格

  • 継承のないクラスベースのオブジェクト指向言語。多態はインターフェースの実装で行い、再利用は委譲で行う。
  • フィールドは let（不変）と var（可変）を明示する。状態が変わる場所は、そのクラスのメソッド内の self.x = ... に限られる。
  • 静的型付け。すべての宣言に型を書く。

M1 の範囲

M1 は、言語からエミュレータ上の画面までを最小限で貫く縦切りとする。ゴールは 09 ロードマップの完了条件を満たすこと。

M1 に含めるもの

  • 型：Int、Bool、String、Unit、Action、Handler<T>、List<T>、利用者定義のクラス
  • クラス、let / var フィールド、メソッド、組み込みインターフェース Screen の実装
  • if / else、while、for、算術、比較、論理演算、リスト記法、メソッド参照
  • リストと文字列の基本的な組み込みメソッド
  • UI 部品：Column、Row、Text、Button、入力欄、スクロール、色・余白・大きさ・配置を指定する部品（05）
  • 変わった部分だけを更新する再描画
  • 画面を回転しても状態が保たれること
  • kata check と kata build、JSON 形式の診断

M1 に含めないもの

  • enum、match、Option、Result、利用者定義のインターフェース、ジェネリクスの自作、ラムダ、break / continue
  • 複数モジュール（利用者のモジュール同士の import）
  • Java 連携、リソース（画像、多言語文字列）、リリース署名、複数画面、通信や保存などの副作用、増分ビルド
